# Implementation index and phase map

**Purpose.** One page that answers "what does this identifier mean, which doc
owns it, and what has actually landed on `dev`?" The wallet/staking work spans
several plan documents whose numbering schemes evolved independently; this
index is the disambiguation layer. It is a *map*, not a status-of-record —
each track's own plan doc remains authoritative for design detail, and where
a plan doc's status table disagrees with landed code, **code wins** (§6 lists
the known disagreements at the verification date rather than editing those
docs from here).

**Method note (2026-07-18) — gate rows decay at the referenced item's rate.** A gate row
("blocked on X", "X is unbuilt") is a claim about *another* item's state and goes stale
when that item moves, not when its host document does. The **cleared-gate sweep is a
landing obligation of the PR that clears the gate**, not of the docs that name it: a PR
that builds or lands X must grep for rows naming X as a blocker (docs *and* code
comments) and correct them in the same landing. Blocked-when-actually-unblocked is the
expensive direction — nobody re-checks a gate that says it is closed. (Instances swept
2026-07-18: the M1 `K_COVER` gate list, the SP-R0 "SP-6 unbuilt" rows in FOLLOWUPS and
the 2D2 plan §2/§12, the WI-1 "made the chain live" comment — PR #333 and the SP-R0
Round-0 exit.)

**Verification stamp.** Statuses below were verified against landed code on
`dev` = `13c368707` (the PR #277 merge) as of 2026-07-09 for the
reward-emission rows (C-1 landed: whitelist flip at
`cryptonote_format_utils.cpp:706`, connect arm `apply_archival_emission_claim`
in `blockchain_db`) and the M1 / segment-freeze rows (PR #263 `6b6517bfc`
/ #264 `0d224faac` merged); other rows retain their prior code-anchored stamps
unless noted. When you update a status here, re-verify against code
(`git grep`, not plan prose) and move this stamp.

**Maintenance discipline** (institutionalized as
[`.cursor/rules/94-tracking-index.mdc`](../../.cursor/rules/94-tracking-index.mdc) —
new identifier families register here at birth; Phase 3+ / Stage 3+ work
items start with an index row).

- **Row format:** every status cell *leads* with the current status and its
  as-of date (e.g. `Landed (as of 2026-08-01)`); dated `UPDATE YYYY-MM-DD:`
  entries append *below/after* that line as the history chain. Readers get
  the answer without parsing the chain.
- **Two verification classes:** *code-anchored* items cite a `git grep`
  target on `dev`; *decision-anchored* items (round closures, wire freezes,
  contract docs — no code artifact) cite the commit hash or PR number of the
  doc edit that closed them.
- **Section contract:** rule 94 refers to §2 (identifier-family registry),
  §4–§5 (live / built-unwired / missing inventory), and §6
  (known-stale-statuses ledger) by role. Their meanings — and this numbering
  — are load-bearing; a restructuring that moves them updates
  `.cursor/rules/94-tracking-index.mdc` in the same PR.
- This doc never carries design content — link to the owning doc instead.
- New identifier families (a new prefix series in any plan doc) get a §2 row
  in the same PR that introduces them, after the rule-94 prefix-uniqueness
  check.

Two independent schemes both used the bare tokens `2a / 2b / 2c / 2d`, and
one token (`2c-2b`) was reused *within* a single scheme:

| Token | Engine-layer meaning (`WALLET_REWRITE_PLAN.md`) | Bond-construction meaning (`ARCHIVAL_BOND_PR2_CHAIN.md`) |

| 2c | Phase 2c — addresses/proofs | Bond-PR 2c-1 / 2c-2a / 2c-2b — real-tree KAT, Model D wiring, request path |
| 2d | Phase 2d — cold bundles | Bond-PR 2d-1 / 2d-2 — `P`-scan layer, `P`-isolated transport |

**Resolution (pinned 2026-06-19, `ARCHIVAL_BOND_PR2_CHAIN.md` §0):** the bond
chain is prefixed **`Bond-PR`** in doc prose; bare **`Phase 2x`** always means
the engine layer. Branch names are immutable history and keep their original
(unprefixed) names.

**The `2c-2b` double-use.** Within the bond chain itself, `2c-2b` names two
different deliverables in sequence:

1. **Bond-PR 2c-2b (request path)** — JoinMarket bond request layer, landed
   `feat/archival-bond-request` #163, plan doc
   [`ARCHIVAL_BOND_REQUEST_2C2B_PLAN.md`](ARCHIVAL_BOND_REQUEST_2C2B_PLAN.md).
2. **2c-2b re-scope (GF-7 scheduler seam)** — block-timed entry-seam planning
   plus GF-7 measurement hooks, landed PR #255 (2026-07-05), plan doc
   [`ARCHIVAL_BOND_2C_GF7_HOOKS.md`](ARCHIVAL_BOND_2C_GF7_HOOKS.md).

When you see `2c-2b` in prose, the linked plan doc disambiguates; new prose
should say "request path" or "GF-7 seam" explicitly.

## 8. Verified-complete archive policy

This section is the durable home of the **verified-complete archive policy**
previously named only in commit messages (`29d267de8`, `675075610`,
`f9f7085df`). Completeness ≠ archival. Living contracts of record stay in
`docs/design/` forever even when implementation is done.

### What belongs where

| Keep in `docs/design/` | Move to `docs/completed/` |
| --- | --- |
| Living specs / contracts of record (e.g. `ARCHIVAL_CONSENSUS_STATE`, `REWARD_EMISSION_LEG`, `DAEMON_SUBMIT_VERDICT`, wire formats) | Finished plan / closeout / preflight / pin / retired-concept record |
| Active umbrellas with open phases (`WALLET_REWRITE_PLAN`, Gate-6, …) | Track whose *owned* work is closed; residues live elsewhere (FOLLOWUPS / sibling SoT) |
| Mixed docs (“landed” + named open residue owned by *this* doc) | Superseded-do-not-implement historical records (after link repair) |

### Eligibility (all three required)

1. **Self-check.** Status banner ∈ {RETIRED, CLOSED-as-record, Round CLOSED
   with no owned open work}; no “DRAFT / in review / pending phase” that
   *this* doc still owns.
2. **Index agreement.** A §2/§4/§5 row (if any) agrees, or the doc is a pure
   closeout sibling of an already-archived track.
3. **Code verify on `dev`.** For landed claims, `git grep` the symbols/PRs;
   for retired claims, confirm absence (or tombstone) as the doc asserts.
   Doc-prose alone is insufficient (rule 94).

### Non-goals

- Do **not** archive by “implementation landed” alone — that is the living-SoT
  hold rule.
- Do **not** rewrite historical CHANGELOG narrative that says a doc “was under
  `docs/design/`” unless the CHANGELOG entry is a clickable relative link that
  would 404 after the move.
- Do **not** bulk-move an entire directory in one PR; batch by risk class
  (retired → closed audits → Stage 0/1 siblings).

### Move checklist

1. Confirm eligibility triad above for each file.
2. `git mv docs/design/X.md docs/completed/X.md`.
3. Rewrite inbound references: `rg -l 'X\.md'` under `docs/`, `.cursor/rules/`,
   and any CI/script path citations that use a `docs/design/` prefix. Prefer
   path-correct markdown links; basename-only code comments
   (`ARCHIVAL_FOO.md §N`) may stay (the M5 citation gate resolves by basename
   under `docs/`).
4. Fix relative links *inside* the moved file (`../design/` for living SoTs;
   sibling completed docs stay same-directory; `../../.cursor/rules/` depth is
   unchanged).
5. Update this index (§2/§4/§5/§7 rows that listed the file under `design/`).
6. Spot-check: no remaining clickable `docs/design/X.md` (or
   `](X.md)` from a file that assumed co-location in `design/`) for moved `X`.
