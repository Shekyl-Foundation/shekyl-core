- **A pull request merges on its owner's `merge-ready` label, which GitHub holds to the head** (ruled 2026-11-19). Pull requests were merged when the required checks went green while other workflows and fleet runs on the same head were still going. The owning lane now applies the `merge-ready` label when every check on the current head has concluded, its fleet and local runs are done and its review threads are resolved. `merge-ready.yml` keeps a commit status of the same name: pending without the label; refused, with the label taken off and a comment naming each reason, while any check runs or is red, a review thread is open or the pull request is a draft; and back to pending when a push takes the label off, with a comment. It is a status rather than a job, so it can never be skipped into a pass (`scripts/ci/merge_ready.py`).
- **The `merge-ready` label re-tests the pull request against the newest `dev`, and so does every later merge that reaches it** (ruled 2026-11-19). A label that passes its check re-tests the head merged with the newest `dev`, on the tests both changes reach; the status is success when that passes, at once when nothing is shared, and otherwise the label comes off with a comment naming the merges and the failing tests. Each push to `dev` re-tests every labelled pull request it shares a test with, after setting it back to pending naming the merge (`merge-ready-dev.yml`); labelled pull requests it does not reach are untouched. One re-test per pull request runs at a time, the newest, and it covers everything merged since the head was last ready (`scripts/ci/merge_ready_overlap.py`, `merge-ready-retest.yml`). This replaces the `merge-next` label, the `fresh-against-dev` status and `rust-pass`'s read of it: nothing marks a pull request merely behind `dev` any more.
