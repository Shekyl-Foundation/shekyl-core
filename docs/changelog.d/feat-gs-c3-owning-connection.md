- **`shekyl-spawn`: one spawn lock per process, shared by every launcher** (Rick, 2026-11-13; `TOR_SUPERVISOR.md` §4.7, `GUI_SYNC_LANE.md` GS-C3). The spawn lock, the child's descriptor hygiene, and the connected pair with its spawn window move out of `shekyl-tor-control-client` into a leaf crate (std, libc and windows-sys only), so the managed Tor's launch and a GUI's launch of the daemon hand a child its end the same way. The crate's contract: one lock per process, and a holder only spawns under it. The managed Tor's launch is unchanged in behaviour.
- **The owning connection** (`INPUT_GRAMMAR.md` IG-Q106; `GUI_SYNC_LANE.md` GS-C3). `shekyld --owning-connection N` adopts an inherited end of a connected stream socket pair as its first act, close-on-exec, so no child it starts holds a copy; writes `shekyld-ready 1` once its owner's socket is served; and stops cleanly when the process that started it closes its end or dies. Command line only, refused with `service`; a number that is not a connected stream socket is refused naming why (`config.owning-connection.unusable`).
- **"This computer", the client's dial** (`RPC_CHANNEL.md` RT-15). `shekyl-rpc-transport`'s `local::LocalTarget` finds a run-as-me daemon by the daemon's own rendezvous naming and calls it on the owner's leg, one connection per call. "Not running" and a failed peer check are distinct failures; the peer check's is a security failure and is never retried. The rendezvous naming and the Windows record moved to `shekyl-rpc-channel`'s `rendezvous`, the session-directory read and the local HTTP exchange to `local`, so the daemon and every client read one copy.
