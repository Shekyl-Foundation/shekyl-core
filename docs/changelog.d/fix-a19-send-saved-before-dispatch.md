- **A send is saved before its bytes leave; a held send asks the user; a stop signal closes the wallet** (alpha.11 bug hunt §A19, wallet lane PR 1). On alpha.11 a send's record, its retained tx secret and its input lock lived in memory until the wallet closed, and `shekyl-wallet-rpc` wired no signal handler: a stopped server lost the OUTBOUND proof for a payment that settled, and the lock, so the next send re-selected the input and was refused as a double spend (sends 7–9's `-29106`, whose `double_spend_conflict` cause the wallet sent and its clients dropped). Now `TransactionSubmitter` takes `DurableTxBytes`, minted only by a successful save of the dispatch record (the journal row with the signed bytes, the secret, the inputs) or by a sealed staking post; a failed save sends nothing (`-29120 SEND_NOT_SAVED`, the reservation kept), and the verdict is saved before the submit returns (`verdict_saved`). The in-memory held-bytes store is deleted: the bytes live on the record (`SEND_JOURNAL_BLOCK_VERSION` 6, `WALLET_LEDGER_FORMAT_VERSION` 25), pruned by its state. After a restart a held send is the user's decision: open locks a send whose verdict never arrived, the watchdog alarms `DispatchedBeforeThisSession` instead of resending, and the contract (0.18.0) lists the held sends (`tx_alarm`) and resends one (`tx_resend`); `shekyl-cli` gains `tx alarm` and `tx resend`, and words a refusal's cause. SIGTERM, SIGINT and SIGHUP (and the Windows console's close, logoff and shutdown events) close the open wallet before the server exits; a second signal exits at once; the CLI's in-process server does the same. The watchdog's confirmed-absent release and the bond record are saved with a rollback on failure, and the daemon's submit log names a rejection's cause.
