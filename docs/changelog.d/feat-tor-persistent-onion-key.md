- **A managed Tor can publish a persistent onion: `tor-onion-key-file`** (`TOR_SUPERVISOR.md` `TSR-Q15`, `INPUT_GRAMMAR.md` IG-Q113). Under `tor = managed`, the option names Tor's own `hs_ed25519_secret_key`, and the daemon publishes that onion at every boot, as a seed node's compiled onion needs, from the Tor it supervises. The key is read once, through a handle judged first: only this account and the superuser may reach it, so a systemd credential qualifies. A key named and not usable refuses the start with its own code (`config.onion-key.missing`, `.unreadable`, `.exposed`, `.not-a-key`), never a fallback to a new onion. The onion's guards persist with it (`TSR-Q2`, `TSR-Q8` amended): Tor's `state`, kept in `tor-guard-state-<service id>` beside the directory cache. A second host on the same key is named, never raced: the onion's cause `published-elsewhere` (`CORE_RPC_VERSION` 4.9), and nothing is republished against it; a named clock or a refused round keeps its cause over it. Second-layer guards are still drawn at every start, so a persistent onion is not yet recommended with clearnet off.
- **The bundled Tor is Expert Bundle 16.0.1 (tor 0.4.9.16) on Linux and Windows**, and the floor device's `linux-aarch64` leaves the alpha line: 16.0.1 is the first stable bundle that ships it. macOS stays at 15.0.26 until its signed pair is re-signed.
