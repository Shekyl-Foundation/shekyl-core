- **A managed Tor can publish a persistent onion: `tor-onion-key-file`** (`TOR_SUPERVISOR.md` `TSR-Q15`, `INPUT_GRAMMAR.md` IG-Q113). Under `tor = managed`, the option names Tor's own `hs_ed25519_secret_key`, and the daemon publishes that onion at every boot, as a seed node's compiled onion needs, from the Tor it supervises. The key is read once, opened and judged before any byte is copied: on Unix the open handle is judged first (only this account and the superuser may reach it, so a systemd credential qualifies); on Windows the open handle is judged in one read, a directory or a reparse point is refused, and the file cannot be renamed or written while it is held. A key named and not usable refuses the start with its own code (`config.onion-key.missing`, `.unreadable`, `.exposed`, `.not-a-key`), never a fallback to a new onion. The onion's guards persist with it (`TSR-Q2`, `TSR-Q8` amended): Tor's `state`, kept in `tor-guard-state-<service id>` beside the directory cache, and a clean stop, a respawn's as well as the daemon's, writes that state back with the directory cache. A second host on the same key is named, never raced: the onion's cause `published-elsewhere` (`CORE_RPC_VERSION` 4.9), and nothing is republished against it, nor does the overdue check fire while it is named; a named clock or a refused round keeps its cause over it. Second-layer guards are still drawn at every start, so a persistent onion is not yet recommended with clearnet off.
