- **The managed Tor's clock line is said once, in one sentence** (`TOR_SUPERVISOR.md` §4.4, §5 "Clock skew"). With this computer's clock three days behind, the node said the clock 11 times in 3.5 minutes on Windows and 18 times in 4 minutes on macOS, each line carrying "The clock is off by -259201 seconds. Check time sync." beside a second clock sentence. The line now says the clock once while it stands, and the recovery once when Tor is up after the clock is set right: "This computer's clock is 3 d 0 h behind the Tor network's. Others may not be able to reach this node. Check this computer's date and time." The figure is Tor's when Tor gave one, and the node's own lower bound otherwise. A clock ahead is said "ahead of". While Tor is starting, a bootstrap problem or an unreachable directory no longer replaces the clock with "cannot reach the Tor network". A clock named after a block, while Tor is starting, replaces the block in the line. Tor's own report of the clock stands until Tor is up, so a consensus that ages, or a sleep, does not make the same fault be said again.
- **`generateblocks` reports success when its block connected, whatever a withdrawal raced it to** (`shekyl-daemon-rpc` `mining_methods.rs`). The call waits for the tip to reach its target or for the mining job to be withdrawn. When the pass that connects the target block also withdraws the job, either could be read first, and a call that had mined its block could return `NotReady`. A caller that retried then mined one block too many: the regtest sync rig's source reached 102 blocks for 101. The chain at the stop now decides. A withdrawal with the tip short of the target is still refused.
