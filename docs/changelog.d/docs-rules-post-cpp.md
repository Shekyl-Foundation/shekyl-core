- **Rules 35, 36, 45 and 93 state the tree without C++** (ruled 2026-11-08). Rule 36 is a Rust rule: secret key bytes, and material derived from them, are clamped, reduced, hashed and combined only in the crypto-owning crates, and every other crate passes typed values. A new gate, `scripts/ci/check_secret_byte_locality.py`, replaces the deleted C++ clamp lint: it scans every production `.rs` file outside those crates for the clamp on byte 0 or 31 and for a scalar reduction whose argument names a secret, and holds the sites that exist to `docs/ci/secret-byte-locality.tsv` in both directions. The inventory is residue only: nine rows (the transaction key reduced for `R = r·G` in five places, the spend secret combined into `x = ho + b` in two, the genesis tool's two), each naming the secrets-storage PR (`SSR-R1`) that moves it into `shekyl-crypto-pq`, and no permanent or exception row. Rule 45 takes rule 25's wording on `unsafe`: every crate root denies `unsafe_code`, and code that calls the operating system or a C library allows it on the item that makes the call, with a `SAFETY` comment. Thirty-five crate roots that hold no `unsafe` now deny it; seven crates that make operating-system or C calls do not yet, and the rule names them. Rule 35 drops its C++ and FFI sections, and rule 93 keeps its lasting part: never introduce a `MONERO_*` identifier, and frozen domain separators stay.
- **Rule 40 is retired** (ruled 2026-11-08). The FFI surface it governed is deleted; its one live sentence, "do not add a C ABI to reach a Rust crate", is in rule 25, and its body is the record `docs/completed/RULE_40_FFI_DISCIPLINE.md`. Rule 35's OS-level section stays a requirement and names its implementation: every binary calls `harden_process` first, and the long-lived secret types in `shekyl-crypto-pq` own locked, dump-excluded storage. That storage, and the move of the nine key reductions the inventory holds behind typed constructors, are the secrets-storage round (`SECRET_STORAGE.md`, `SSR-`), which lands after the alpha.12 cut; the `unsafe` scoping of five operating-system crates follows it, and rule 45 names the two RandomX C-reference crates as its only crate-level allows. `AllKeysBlob`'s doc no longer claims a C++ `mlock`'d allocation.
- **Rule 25 takes rule 40's decoder sections, re-scoped to every decoder of untrusted bytes** (ruled 2026-11-08): bound a decoded count before it sizes an allocation (the backing bound and a protocol ceiling, whichever is tighter), no crate- or module-wide allow of the cast lints in a decoder, and refuse, never panic, on malformed input. The FFI-only bullets are dropped. The source-scan gate for the reserve rule lands in the `unsafe` scoping PR (`SSR-R2`).
- **Rule 20 is retired** (ruled 2026-11-08). It chose between Rust and C++, and the C++ is deleted. Its live sentence is rule 25's opening, which alone names `scripts/ci/check_no_first_party_c.py`; its section "A new subsystem is its own change" is rule 26's and applies whether or not the rest of rule 26 is cited; its body is the record `docs/completed/RULE_20_RUST_VS_CPP.md`. Rules 17, 43, 45 and 70, `CLAUDE.md`, and the Rust comments that justified a shape by rule 20 now state the reason itself; every link to the rule points at the record.
- **The onion keypair moves into `shekyl-crypto-pq`** (ruled 2026-11-08). The RFC 8032 expansion of an onion seed and its public key are secret-byte operations, so `shekyl-crypto-pq` owns them: `onion::OnionKeypair` holds the expanded 64-byte secret on the heap (wiped on drop, no `Debug`, no `Clone`) and the Ed25519 public key, computed from the expanded secret. A persona's keypair comes from `archival_p::derive_p_onion_keypair`, and the persona bundle holds the keypair, so the derived seed never leaves the crate (`derive_p_hs_id_seed` survives only under the test-only `test-utils` feature, for the frozen vectors). The daemon's per-boot onion comes from `OnionKeypair::ephemeral`, which draws its seed from the OS CSPRNG, and the daemon holds an `OnionIdentity` for the boot instead of a seed. `shekyl-tor-control-client`'s `OnionIdentity` is built from a keypair and hashes, clamps and multiplies nothing secret; the three Tor clamp rows leave `docs/ci/secret-byte-locality.tsv`. No `.onion` address changes: a known-answer test pins the fixed-seed address and that the public key from the expanded secret equals `SigningKey::from_bytes(seed).verifying_key()`, and the `ARCHIVAL_P_DERIVE_V2` public-key vectors are checked against the free function and the bundle.
