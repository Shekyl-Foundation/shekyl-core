- **A file the daemon replaces is replaced in one place, and a scanner that holds it is waited for** (`shekyl-os-account`, `shekyl-win-sec`, `shekyld`; Rick, 2026-11-18). On Windows a program that opened a freshly written rendezvous file without delete sharing (an antivirus scanner, a search indexer) failed the start with a sharing violation, blamed the directory with a Unix remedy, and left `shekyl-<name>.<pid>.new` behind for good. `StagedWrite::commit` is now the only place a file is replaced. On Windows it renames through the handle (replace-if-exists, POSIX semantics; the classic rename on FAT32 and exFAT), so a reader of the old file that shares delete does not block it. Removing a leftover staged file and the rename share one 2 s deadline, waiting for a reader that does not share delete (a reader of the staged file this process is writing fails its own open instead; see below). Past it the start refuses with `config.replace.held-open`, naming the file held and the directory to exclude from scanning. A file whose read-only attribute is set is refused at once with `config.replace.read-only`, which says to clear the attribute: the replace reads the attribute when the rename is refused (an access denial; on FAT32 a collision), so a read-only file is never waited out as a held one. A stale owner's record is replaced by the publish under the same wait, no longer refused as an impostor when a scanner holds it. A staged file's kind is in its type: a journal (the console key) is resumed at a start and never discarded on a failure; a replace (a rendezvous record, the console leg's name, the bundle) is removed by the next start's write and by its own failed commit.
- **Six more crates replace their files through that one replace** (`shekyl-daemon-config`, `shekyl-dialer`, `shekyl-tor-control-wallet`, `shekyl-engine-prefs`, `shekyl-chain-ingest`, `shekyl-engine-file`; Rick, 2026-11-18), and `rust/clippy.toml` refuses `std::fs::rename` and tempfile's `persist` family everywhere else, a rename that is not a replace carrying an allow that names why. No file's protection changes. The data directory's network marker keeps its syncs. The dialer's address file, written before with no sync at all, is now synced before the rename and its directory after. The vanguard state file's staged copy is a journal: a failed save keeps it and the next start recovers the set from it, as it did from the old `.state.tmp`. The wallet preferences pair keeps its owner-only mode and its syncs. A rebaseline trace and a height-digest table publish through one staged name per file, one publisher per path. A wallet file is staged as `<name>.new` and, on Windows, renamed through the handle that supersedes the keys file under a live lock during password rotation, with no `FILE_ATTRIBUTE_TEMPORARY` to clear; `WalletFileError::AtomicWriteFinalizeStaged`, which only that clear produced, is gone.
- **A refused start is in the log file** (`shekyld`). Every refusal or failure that ends a start reached standard error alone, which a service's operator may never see. It now also reaches the log file once the configuration names one; `--config-verify` still writes nothing.
- **A Windows replace is durable through the handle that created its staged file** (`shekyl-win-sec`, `shekyl-os-account`, `shekyl-engine-file`, `shekyl-engine-core`, `shekyl-tor-control-client`; Rick, 2026-11-18). A staged file is created with write and delete access, `FILE_FLAG_WRITE_THROUGH` and its descriptor, sharing read only, and that one handle writes and flushes the data, renames the file over its destination, flushes again and closes; no commit reopens a staged file it created. A scanner that opens the staged file without delete sharing now fails its own open instead of holding the commit, and no other program can open it to write or delete it; the one exception is the wallet's password rotation, whose staged keys file also shares write so the rotation's lock can open it for reading and writing (`StagedWrite::create_with`, `Sharing::ReadWrite`); only a journal left by an earlier start (the console key's) is reopened, with the wait. A replace is reported durable only on a local NTFS volume, on the POSIX rename, with the flush after it returned, citing `CreateFileW`'s documentation that a write-through handle's rename is flushed; the post-rename flush is a second layer Microsoft does not document for renames. A network drive (`FILE_REMOTE_DEVICE`) is never confirmed, whatever file system it reports: a Samba share reports NTFS. FAT32, exFAT, ReFS and any other file system report the replace unconfirmed, naming the file system. A wallet on such a volume still saves, and refuses to send: the wallet engine's refusal names the file system the wallet is on and says to move the wallet to an NTFS volume, and over the wallet RPC it is `-29128 SAVE_DURABILITY_UNCONFIRMED` with the file system in `data.file_system` (below). The Tor directory cache saves through the same creating handle, owner-only as before and under its own staged names, instead of `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`; a link at a cache file's name is replaced by the rename itself, so the step that removed it first, and the crash window between the two, are gone.
- **Every cause of an unsaved send has its own wallet RPC code and advice** (`shekyl-engine-file`, `shekyl-wallet-contract`; Rick, 2026-11-18 and 2026-11-19). `-29120 SEND_NOT_SAVED` told every unsaved send to make the wallet directory writable or free disk space. It is now `-29120 SAVE_NOT_WRITABLE`, for a wallet folder, file or drive this account cannot write, with `data.target` (`folder`: make it writable; `file`: its read-only attribute is set, clear it; `volume`: the drive is read-only or write-protected). `submit_pending_tx` gains `-29128 SAVE_DURABILITY_UNCONFIRMED` (a local Windows volume other than NTFS; `data.file_system`; move the wallet to an NTFS volume), `-29129 SAVE_DISK_FULL` (free disk space), `-29130 SAVE_FILE_HELD` (another program, most likely a scanner, held the wallet's file past the save's wait; exclude the wallet's folder from scanning), `-29131 SAVE_IO_FAILED` (the disk's error at a step: `data.step` is `write`, `rename`, `folder-sync`, `flush` or `volume-query`, and the message names it; `data.error` is the system's words, never a path; check the disk), `-29132 SAVE_RENAME_UNCONFIRMED` (a local NTFS drive that refused the rename Windows confirms; move the wallet to another local NTFS drive), `-29133 SAVE_INTERNAL_FAULT` (the wallet could not prepare its record before touching the disk; report it) and `-29134 SAVE_ON_NETWORK_DRIVE` (a network drive; move the wallet to a local drive). Each sent nothing and keeps the reservation. The wallet contract is 0.21.0, still unreleased. The engine types what the contract maps, so no code is inferred from an error's kind alone: `WalletFileError::SaveStep` names the step that failed (it replaces `AtomicWriteRename`, which named only the rename), `WalletFileError::ReadOnly` a read-only wallet file, `WalletFileError::HeldOpen` another program's hold, and `shekyl_engine_file::Unconfirmed` each Windows cause (`Remote`, `ClassicRename`, `Flush`, `VolumeUnread`, `Reopened`).
- **A staking seal that was not confirmed on disk sends nothing and reopens its lane** (`shekyl-engine-core`, `shekyl-wallet-contract`; Rick, 2026-11-19). A bond post, claim, drain or exit whose seal was saved but not confirmed sent nothing, yet the claim, drain and bond post kept the seal, and `unstake` answered `-29522 UNSTAKE_FATE_UNKNOWN` ("sent, held") while `drain` and `collect_unstaked` answered `-29107 SUBMIT_AMBIGUOUS`. Every such seal is now removed, so the lane reopens, and `stake`, `unstake`, `drain` and `collect_unstaked` answer with the save's own code by cause, worded for a retry. A seal whose save fails outright (a read-only file, a full disk) answers by cause too, no longer as an internal fault. A staking record read back from disk is sent only after a save of the pending records confirmed in this process covers it: the wallet saves them once at open for that, and the bond-post driver neither marks nor sends a record while they are uncovered, so on a FAT volume or a network share no staking bytes leave.
- **Supported storage is stated** (Rick, 2026-11-19): a local NTFS volume on Windows, a local disk on Unix. On anything else the wallet still saves, refuses to send or stake with the code for the cause, and its message says why; the daemon still starts and logs a warning for each file it replaced whose save is not confirmed, naming the file and why; network shares are not a supported configuration (`INSTALLATION_GUIDE.md`, "Supported storage").
- **On Windows a service's rendezvous record is a registry value** (`shekyl-rpc-rendezvous`, `shekyl-win-sec`, `shekyld`; Rick, 2026-11-18). A local account could hold a world-readable record file open without delete sharing and so block the service's publish; the record is now a value under `HKLM\SOFTWARE\Shekyl\Rendezvous`, written whole and removed whatever readers hold the key. The installer creates the key with the service account (RT-W14); the daemon checks it before publishing and refuses a missing or exposed key with `config.service.rendezvous-key`. Linux, FreeBSD and macOS keep the single file. One reader API (`ServiceRecordAt`) serves both, and the withdrawn `%ProgramData%\shekyl\rendezvous` directory is gone from the code.
