- **A file the daemon replaces is replaced in one place, and a scanner that holds it is waited for** (`shekyl-os-account`, `shekyl-win-sec`, `shekyld`; Rick, 2026-11-18). On Windows a program that opened a freshly written rendezvous file without delete sharing (an antivirus scanner, a search indexer) failed the start with a sharing violation, blamed the directory with a Unix remedy, and left `shekyl-<name>.<pid>.new` behind for good. `StagedWrite::commit` is now the only place a file is replaced. On Windows it renames through the handle (replace-if-exists, POSIX semantics; the classic rename on FAT32 and exFAT), so a reader of the old file that shares delete does not block it. Removing a leftover staged file and the rename share one 2 s deadline, waiting for a reader that does not share delete (a reader of the staged file this process is writing fails its own open instead; see below). Past it the start refuses with `config.replace.held-open`, naming the file held and the directory to exclude from scanning. A stale owner's record is replaced by the publish under the same wait, no longer refused as an impostor when a scanner holds it. A staged file's kind is in its type: a journal (the console key) is resumed at a start and never discarded on a failure; a replace (a rendezvous record, the console leg's name, the bundle) is removed by the next start's write and by its own failed commit.
- **Six more crates replace their files through that one replace** (`shekyl-daemon-config`, `shekyl-dialer`, `shekyl-tor-control-wallet`, `shekyl-engine-prefs`, `shekyl-chain-ingest`, `shekyl-engine-file`; Rick, 2026-11-18), and `rust/clippy.toml` refuses `std::fs::rename` and tempfile's `persist` family everywhere else, a rename that is not a replace carrying an allow that names why. No file's protection changes. The data directory's network marker keeps its syncs. The dialer's address file, written before with no sync at all, is now synced before the rename and its directory after. The vanguard state file's staged copy is a journal: a failed save keeps it and the next start recovers the set from it, as it did from the old `.state.tmp`. The wallet preferences pair keeps its owner-only mode and its syncs. A rebaseline trace and a height-digest table publish through one staged name per file, one publisher per path. A wallet file is staged as `<name>.new` and, on Windows, renamed through the handle that supersedes the keys file under a live lock during password rotation, with no `FILE_ATTRIBUTE_TEMPORARY` to clear; `WalletFileError::AtomicWriteFinalizeStaged`, which only that clear produced, is gone.
- **A refused start is in the log file** (`shekyld`). Every refusal or failure that ends a start reached standard error alone, which a service's operator may never see. It now also reaches the log file once the configuration names one; `--config-verify` still writes nothing.
- **A Windows replace is durable through the handle that created its staged file** (`shekyl-win-sec`, `shekyl-os-account`, `shekyl-engine-file`, `shekyl-engine-core`, `shekyl-tor-control-client`; Rick, 2026-11-18). A staged file is created with write and delete access, `FILE_FLAG_WRITE_THROUGH` and its descriptor, sharing read only, and that one handle writes and flushes the data, renames the file over its destination, flushes again and closes; no commit reopens a staged file it created. A scanner that opens the staged file without delete sharing now fails its own open instead of holding the commit, and no other program can open it to write or delete it; the one exception is the wallet's password rotation, whose staged keys file also shares write so the rotation's lock can open it for reading and writing (`StagedWrite::create_with`, `Sharing::ReadWrite`); only a journal left by an earlier start (the console key's) is reopened, with the wait. A replace is reported durable only on NTFS, on the POSIX rename, with the flush after it returned, citing `CreateFileW`'s documentation that a write-through handle's rename is flushed; the post-rename flush is a second layer Microsoft does not document for renames. FAT32, exFAT, ReFS and any other file system report the replace unconfirmed, naming the file system. A wallet on such a volume still saves, and refuses to send: the wallet engine's refusal names the file system the wallet is on and says to move the wallet to an NTFS volume, and over the wallet RPC it is `-29128 SAVE_DURABILITY_UNCONFIRMED` with the file system in `data.file_system` (below). The Tor directory cache saves through the same creating handle, owner-only as before and under its own staged names, instead of `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`; a link at a cache file's name is replaced by the rename itself, so the step that removed it first, and the crash window between the two, are gone.
- **Every cause of an unsaved send has its own wallet RPC code and advice** (`shekyl-engine-file`, `shekyl-wallet-contract`; Rick, 2026-11-18). `-29120 SEND_NOT_SAVED` told every unsaved send to make the wallet directory writable or free disk space. It now answers only a wallet folder this account cannot write (or a read-only volume), and `submit_pending_tx` gains `-29128 SAVE_DURABILITY_UNCONFIRMED` (a Windows volume other than NTFS; `data.file_system`; move the wallet to an NTFS volume), `-29129 SAVE_DISK_FULL` (free disk space), `-29130 SAVE_FILE_HELD` (another program, most likely a scanner, held the wallet's file past the save's wait; `data.or_unwritable` on FAT32 and exFAT, where a read-only file answers the same; exclude the wallet's folder from scanning), `-29131 SAVE_IO_FAILED` (the disk's error, a Unix folder sync or a Windows flush among them; `data.error`, the system's words, never a path; check the disk), `-29132 SAVE_RENAME_UNCONFIRMED` (an NTFS drive that refused the rename Windows confirms; move the wallet to a local NTFS drive) and `-29133 SAVE_INTERNAL_FAULT` (the wallet could not prepare its record before touching the disk; report it). Each sent nothing and keeps the reservation. The wallet contract is 0.21.0, still unreleased. The engine types what the contract maps: `WalletFileError::HeldOpen` carries another program's hold (it was an `io::Error` inside `Io` or `AtomicWriteRename`), and `shekyl_engine_file::Unconfirmed` names each Windows cause (`ClassicRename`, `Flush`, `FileSystemUnread`, `Reopened`) instead of wrapping `shekyl-os-account`'s.
