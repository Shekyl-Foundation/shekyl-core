- **Multisig ceremony files show nothing but their version, say who sent them, and are the only transport** (slice 3 PR-B; R-5, R-6, R-9 to R-13, ruled 2026-11-12). A ceremony file is `format_version ‖ nonce ‖ ciphertext ‖ tag` under one XChaCha20-Poly1305 key per group. The fingerprint, intent hash, sender, message type, body and signature are all inside the ciphertext, so a wallet finds a file's group by trial decryption. Each member has a long-term hybrid envelope key from the dealer (member file v2), and every file is signed under `shekyl/multisig-envelope-scheme-v1` over a frame bound to the network. A member who holds the transport secret cannot write a file as another member. Import checks the parse, the fingerprint, the sender index and the signature in order before any body is handed on. Intent v2 names the `m` signers and the responder, and drops the proposer signature, the wall-clock expiry and the `tx_counter`: an intent expires when its reference block ages out, and replay is stopped by that age, the held nonce bound to one intent hash and consensus key images, with a member committing to at most one live intent per input. That age is measured as consensus measures it, from the connecting height; `shekyl-curve-tree`'s `proof_submittable` and `proof_expired` now do so too, pinned by a sweep against CEN-I11. A group needs `m ≥ 2` at the address, the dealer split, the intent and the on-chain container (CEN-I16's floor is now a 2-of-2 blob, 4060 bytes). Message types `0x0C`–`0x11` are assigned. The relays, the relay directory, the persisted message counter and the CounterProof and ProverReceipt machinery are removed from the spec, and an online mailbox is DEFERRED.
