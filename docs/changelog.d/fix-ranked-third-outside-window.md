- **The hasher's third cache place goes to the most-work chain the window does not cover** (`RANDOMX_CACHE_ACTOR.md` §5.1, HA-R2).
  - **What was wrong.** `ranked_seeds` picked the heaviest chain among the held forks and chain sync's frontier, and only then dropped it when the window already named its seed. A synced node's frontier is a peer's run on the node's own chain: always the heaviest, always in the window. So a synced, peered node never listed a held fork's seed, and each block on that fork paid a cache build.
  - **Now.** Chains whose seed the window names are set aside first, and the heaviest of the rest is the third. The order between equals (a fork before the frontier, then the alt table's key order) and the classes are unchanged. A frontier outside the window that outweighs a held fork is still the third, so a fork does not take the place during sync.
