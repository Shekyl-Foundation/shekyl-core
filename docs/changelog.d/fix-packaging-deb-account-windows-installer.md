- **Packages: the daemon's account is declared and never someone's login; the `.rpm` runs the daemon; the Windows installer carries Tor and the tunnel** (`INPUT_GRAMMAR.md` IG-Q64; IG-F12 closed, IG-F13's Linux half; found preparing alpha.12's fleet install). The units run as `shekyl`, which no package created, so on a clean machine `systemctl enable --now shekyld` failed (status 217/USER), and the `.rpm` shipped no daemon unit at all. Both packages now declare the account (`/usr/lib/sysusers.d/shekyl.conf`: a system account with no home and no login shell) and `/etc/shekyl` (`/usr/lib/tmpfiles.d/shekyl.conf`: `root:shekyl` `0750`), apply them after install, and carry `shekyld.service` and `shekyl.slice`. Before any file is unpacked they refuse an existing `shekyl` that is a login (a shell, an administrators' group, a sudo rule) or a `shekyl` group another account uses, because the daemon would run with that login's rights (Rick, 2026-11-18); the refusal names the rename. Neither package enables, starts or restarts the daemon; removal stops and disables it and keeps the account, `/etc/shekyl` and the data. Tested on Debian 12 and 13, Ubuntu 22.04 and 24.04 and Rocky 9 (install, upgrade, removal and each refusal), and on a Rocky Linux 9 host under systemd with SELinux enforcing: the daemon ran as the new account, read its file through `/etc/shekyl`, answered on its view listener, and logged no SELinux denial. The Windows installer copied only the executables, so an installed daemon had no Tor where it looks on Windows (`tor\` beside `shekyld.exe`) and, under the default `tor = managed`, none to run; it now installs the pinned `tor.exe`, its licences and `shekyl-rpc-tunnel.exe`, clears an earlier release's `tor\` first, drops the `shekyl-cli` entries and shortcut Windows never shipped, and the package job checks the installer's Tor against its pin. The package job runs on ubuntu-24.04: 22.04's p7zip 16.02 cannot read the installer and, asked for `tor\` alone, returns wrong bytes.
