- **Packages: the `.deb` creates the daemon's account, and the Windows installer carries Tor and the tunnel** (found preparing alpha.12's fleet install). The `.deb`'s unit runs as `shekyl`, which nothing created, so on a machine without that account `systemctl enable --now shekyld` failed (status 217/USER). Its after-install script now makes a system account with no home and no login shell, once; an existing account is left as it is, and removal keeps it. Tested by installing, upgrading, removing and reinstalling a package built with the release's `fpm` flags on Debian 13 and Ubuntu 22.04 and 24.04. The package neither enables nor starts the daemon, which two comments wrongly said `fpm` did; on upgrade it restarts an enabled one. The Windows installer copied only the executables, so an installed daemon had no Tor where it looks on Windows (`tor\` beside `shekyld.exe`) and, under the default `tor = managed`, none to run; it now installs the pinned `tor.exe` and its licences (removing an earlier release's `tor\` first, which the daemon would refuse), and `shekyl-rpc-tunnel.exe`. It no longer names `shekyl-cli.exe` or `shekyl-wallet-rpc.exe`, which Windows does not ship, nor a shortcut to them, and its uninstaller removes the shortcut the earlier installer made under another name. The package job checks the installer's Tor against its pin, as it does the `.deb` and `.rpm`. `RELEASING.md` now says what each package installs; the `.rpm` carries no daemon unit or account.
