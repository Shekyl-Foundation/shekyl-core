- **CI: every fuzz harness is compiled, against the workspace's dependency versions.** Each `rust/<crate>/fuzz/` is its own workspace outside the main one, so nothing compiled seven of the ten fuzz crates, and an API change in a fuzzed crate could break its harness silently. A new workflow, `fuzz-harness.yml`, type-checks every fuzz crate with `cargo check --locked` on the pinned stable toolchain, one job per crate, in parallel, scoped to the change: a crate's job runs when the change reaches any crate it depends on by path (the scope classifier's reverse closure), touches its own files, or touches what every harness builds against (the workspace lockfile, the toolchain pin, the inventory script, the workflow). `fuzz-harness-pass` is the workflow's one verdict; a job skipped by scope is a pass. The inventory is derived from the tree by `scripts/ci/check_fuzz_inventory.py`, which replaces the hand-written list of 26 file paths in the Rust job: every `[[bin]]` names a target file and every target file is a `[[bin]]` (10 crates, 37 targets), every fuzz crate's `Cargo.lock` is tracked, and every package a fuzz crate shares with the workspace is at a version `rust/Cargo.lock` locks, so the fuzzers exercise the versions that ship and `cargo audit` sees every one. The workflow builds its matrix from that script, so a fuzz crate cannot exist without being compiled. The six missing lockfiles are committed (`shekyl-engine-state`'s `.gitignore` no longer hides its own), and every fuzz lockfile is regenerated from the workspace's by `check_fuzz_inventory.py --regenerate`. The Rust job loses its three fuzz compile steps and their two cache entries.
