- **Multisig (Option E′): an output can be paid to a group, and any `m` of its `n` members can spend it** (`PQC_MULTISIG.md` §6–§8; slice 1 of the E′ completion, rulings R-1 and R-3). A group address now carries a group KEM key (address version `0x02`, `70 + (n+1)·1216` bytes); a payer's output to it is a solo output to the group (one `0x06` ciphertext, `O = ho·G + B_group + (y_group + y_kem)·T`) plus a `0x0D` entry: a KEM ciphertext to each member and the members' per-output key hashes, encrypted. The output's leaf commits to `0x02 ‖ n ‖ m ‖ h_1 … h_n`, so a spend reveals only its signers' keys. Every member finds the output with the solo scanner and checks the entry (`Scanner::new_multisig_member`); a damaged entry leaves the output received but unspendable. The dealer's member file is specified (`shekyl-multisig::member_file`). About 4.7 KB per output at n = 3, 7.0 KB at n = 5.
- **Consensus: the multisig key blob is container version `0x02`** (CEN-I16, CEN-I18, CEN-I15). It is the committed form, a signer bitmap and the signers' keys (`3 + 32·n + 1 + 1996·m` bytes, at least 2032); `verify_multisig` checks each revealed key against its hash under the chain's network id, and both verifiers derive the leaf scalar `k` from the committed form only (`pqc_leaf_key_bytes`, `PqcKeyScalar::from_pqc_auth`). `verify_pqc_auth` takes the network id. CEN-I19 gains the `0x0D` clause: at most one field, not empty, entries ascending by output index and naming outputs the transaction has.
- **Deleted:** tags `0x09` and `0x0A` (never produced; the bytes are never reused), `multisig_receiving.rs`, the container's per-member spend-auth pubkeys, and `InvariantId::I7`.
