- **A merge to `dev` re-tests the open pull requests it can break** (Brief C, option (a), ruled 2026-11-19). Two pull requests each green alone could be red together, and the second merged on a green that predated the first (#1404 and #1409, #1425 and #1426, #1440 and #1447). After each push to `dev`, `freshness.yml` finds the open, non-draft pull requests whose tests reach a crate the push changed (`scripts/ci/freshness_overlap.py`, scoped by `change_scope.py`'s own rules), marks each head's `fresh-against-dev` status pending, and re-tests the head merged with the new `dev` on its own scoped tests (`freshness-retest.yml`). Green posts success; failing tests, a conflict, the time budget or a cancelled re-test post failure, with a comment naming the merge and the failing tests. `rust-pass` now fails unless `fresh-against-dev` is absent or green, so a pull request cannot merge while its re-test runs or after it failed. One re-test runs per pull request at a time, the newest merge's, and the newest `dev`'s result stands whatever order the results arrive in.
- **A red job on `dev` opens its own issue and closes it when green again.** `report-dev-red.yml` keeps one issue per red job (`dev RED: <workflow> / <job>`) instead of one per workflow, assigns it to the Foundation's lead, and names the failing tests from the job's log (`scripts/ci/failed_tests.py`, for nextest and `cargo test`), the failed steps, the commit range since the workflow last passed and the pull requests merged in it. It now runs on every push run on `dev`, red or green, and the job's next green run closes its issue.
