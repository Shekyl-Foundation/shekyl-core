- **A merge to `dev` makes the open pull requests it can break stale, and the `merge-next` label re-tests one** (Brief C, ruled 2026-11-19). Two pull requests each green alone could be red together, and the second merged on a green that predated the first (#1404 and #1409, #1425 and #1426, #1440 and #1447). After each push to `dev`, `freshness.yml` finds the open, non-draft pull requests that share a test with the push, a test both changes reach (`scripts/ci/freshness_overlap.py`, scoped by `change_scope.py`'s own rules), sets each head's `fresh-against-dev` status to stale with one comment per pull request naming the merges and crates, and runs nothing. `rust-pass` now fails unless that status is absent or green, so a stale pull request cannot merge. A re-test runs when the pull request carries the `merge-next` label, on the head merged with the new `dev` and only on the tests both the pull request and every merge since it was last fresh reach; with none, the head goes green without a run. Failing tests, a conflict, the time budget or a cancelled re-test post failure, with a comment naming the merges and the failing tests. A red re-test is the pull request's: the freshness run on the `dev` commit stays green, and goes red only when its own jobs fault. One re-test runs per pull request at a time, the newest, and the newest `dev`'s status stands whatever order the results arrive in.
- **A red job on `dev` opens its own issue and closes it when green again.** `report-dev-red.yml` keeps one issue per red job (`dev RED: <workflow> / <job>`) instead of one per workflow, assigns it to the Foundation's lead, and names the failing tests from the job's log (`scripts/ci/failed_tests.py`, for nextest and `cargo test`), the targets that did not compile, the failed steps, the commit range since the workflow last passed and the pull requests merged in it. It now runs on every push run on `dev`, red or green, and the job's next green run closes its issue.
- **No run on `dev` is cancelled once it runs** (ruled 2026-11-19). The fifteen shorter workflows that pushed on `dev` with `cancel-in-progress: true` now cancel only a pull request's older run, as the build, Rust, fuzz-harness and benchmark workflows already did: one run on `dev` runs, one waits, and a newer merge replaces the waiting one. `scripts/ci/check_dev_push_runs_finish.py` now holds every workflow that pushes on `dev` to that, not a list of four.
- **`contrib/depends/` is the depends jobs' tree.** A row in `scripts/ci/job_owners.tsv` may now claim a whole directory outside `scripts/ci/` and `.github/`; `contrib/depends/` is claimed by `depends:legs` and `depends:build-cross`, so a depends-only change no longer runs every Rust test, and no longer re-tests every open pull request.
