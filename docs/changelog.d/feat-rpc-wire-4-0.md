- **Daemon RPC 4.0: every method and field takes its grammar name, and the wire takes one form** (`RPC_WIRE.md` RW-Q1…RW-Q10, `INPUT_GRAMMAR.md` Parts C and F; `CORE_RPC_VERSION` 4.0). **Breaking for every daemon RPC client:** a 3.x name is method-not-found, and a client refuses a daemon of another version before it decodes anything (RK-D25). The method table and its grants are generated at `docs/generated/rpc_wire_schema.tsv`.
  - **One route, strict JSON-RPC 2.0.** `POST /json_rpc` only: no REST path, no alias, no `.bin` method. `"jsonrpc": "2.0"` and a non-null `id` are required, `params` is a named object or left out, one request per message, and an unknown parameter is refused.
  - **Names.** For example `get_info` → `daemon_status`, `get_block_count` → `chain_height`, the four header reads → `block_header_show` and `block_header_list`, `get_block` → `block_show`, `/get_blocks_by_height.bin` → `block_list`, `/get_transactions` → `tx_show` and `tx_list`, `/is_key_image_spent` → `chain_spent`, `/submit_transaction` → `tx_submit`, `get_block_template` and `get_miner_data` → `block_template`, `calc_pow` → `pow`, `request_archival_shard` → `shard_fetch`, `generateblocks` → `dev_block_generate`, `/pop_blocks` → `dev_chain_pop`. `get_version` is `version`.
  - **Values.** Block and transaction bytes are base64; a height is the tip's ordinal, never a count; an amount is decimal atomic units; a field the caller's grant withholds is absent, and one with no answer is `null`. A list reply has a slot per asked item in order: the item, `{"missing": null}`, `{"archived": {...}}`, or `null`. A block is selected by exactly one of `{"height": h}`, `{"hash": x}` or `{"tip": null}`.
  - **Errors.** A failure is only the error object: its code is one of seven classes (bad params, refused by the method, outside the grant, over a resource bound, not ready, store fault, internal), and its `data` is one diagnostic with a dotted code (`shard.open`, `bound.block`, `pow.seed`, …). No reply carries `status`.
  - **Grants.** The view listener answers the chain, pool, health, submit and mining-work methods, now including `shard_fetch` (moved to `chain`, IG-Q91); the admin listener answers everything.
- **`shard_fetch` serves views on every node with a Tor, bounded** (`INPUT_GRAMMAR.md` IG-Q90). The node builds one fetch scheduler whenever Tor is on, shared with the bundle producer when it mines. Bounded callers share one fetch at a time: a cached view is free, and a call that would open a second fetch is refused `bound.shard`. The producer's reads hold fetch slots no view takes. A node with Tor off refuses `shard.tor-off`. The daemon reserves the fetch client's descriptors on every Tor node.
- **`tx_relay` re-offers a pooled transaction** through the same entry a fresh local submission takes. A caller without the host's view sees an entry not yet public as `{"missing": null}`, and nothing is offered.
- **Wallet RPC 0.17.0:** `-29212 DAEMON_GRANT_REFUSED` for a daemon call outside the wallet's grant; `get_shard_view` gains `-29537 SHARD_VIEW_BUSY` (transient) and the `-29536` cause `tor_off`.
- **Clients moved:** the wallet engine, `shekyl-cli`, `shekyl-wallet-rpc`, the Python framework (`utils/python-rpc`), stressnet, the bench and capture scripts, and the vector generators speak 4.0.
