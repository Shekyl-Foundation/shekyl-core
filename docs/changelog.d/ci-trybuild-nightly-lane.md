- **CI: the long trybuild harnesses run nightly, not on every pull request.** The compile-fail harnesses of `shekyl-chain-rules`, `shekyl-mempool` and `shekyl-crypto-pq` compile their programs as a downstream crate, in a cargo project trybuild builds under `target/tests/trybuild`, where each crate's whole dependency tree compiles again and the workspace's profile does not reach: about 19 minutes per tree on the 4-vCPU runner, twice per run (chain-rules' tree is a `build`, crypto-pq's a `check`, and cargo shares nothing between the kinds; mempool's programs reuse chain-rules' build). Those four tests are now `#[ignore]`d and run every night on `main` and `dev` by the `trybuild-ignored` lane (`scripts/ci/ignored_set_trybuild.sh`, which asserts each trybuild target's ignored set is exactly its list before running it); the per-PR Rust job runs the same script with `--check`, so a pull request that renames, deletes or un-ignores one of them fails until the list is decided. The trade is deliberate: the guarantees these programs pin (an unencrypted output field cannot be built downstream, a verdict connects only under the view it was judged against, a pool verdict never reaches `connect`) are now checked the night after a merge to `dev`, not before it. `shekyl-logging`'s harness checks little (14 s cold) and stays in the pull-request run; the nextest test group that serialised the five is gone with the four. The lane's first run alone found that `shekyl-chain-rules`' programs compile only with the crate's `harness` feature (`Trust::UNPINNED` is a `test`/`harness` item), which the workspace run had been turning on through the store's dev-edge: the trybuild target now requires the feature, and the lane builds each harness with the features its programs need.
